01 · 一句话定位

拍摄现场，按一个按钮，说出你想要的效果，AI 看着当前取景画面，实时告诉你机位怎么调、怎么拍。

这不是一个"生成视频"的工具，也不是一个"自动构图"的滤镜。它是一个现场拍摄教练——把专业摄影师的判断力，翻译成普通人能执行的动作。

产品边界（重要，防止做偏）

维度我们做我们不做
核心动作看当前画面 → 给调整动作自己生成视频画面
输出形式"后退两步 / 换 3.2x / 机位降到腰部" + 理由3D 最优机位坐标
交互时机拍摄中实时建议 + 拍后素材整理与粗剪逐帧精修、调色、特效、生成新画面
素材处理按意图与质量筛选可用片段，输出粗剪时间线替代专业剪辑师完成最终成片
技术路线调用现成模型 API + 自研决策层训练自己的视觉大模型

为什么"找机位"要落地成画面反馈：真实拍摄现场没有现成的 3D 场景结构，AI 不知道你身后是墙还是悬崖。所以只能"看当前画面 → 判断与目标的差距 → 给出可执行动作"。这不是降级，Doka、手机原生 AI 构图等已跑通的产品靠的都是这个逻辑。我们的差异点是意图驱动——不是给所有场景同一套构图线，而是按你说的"电影感特写""产品质感"给不同的建议。

02 · 用户与痛点

短视频创作者

知道要拍得"有感觉"，但说不出 professional 的机位要求。拍完发现画面平淡，不知道问题出在哪。

电商 / 营销商家

一条产品视频能不能带来转化，账算得过来。愿意为"稳定产出能用的素材"付费。

学生剧组 / 摄影爱好者

有审美想法，缺执行经验。需要有人在现场告诉他"再退两步会更好"。

三个真实痛点

  1. 会说想要什么，不会说怎么拍。用户能说出"想要氛围感"，说不出"主体占画面 35%、侧光、机位略低于视线"。
  2. 拍完才知道废了。现有工具要么是拍后重构图（救不回镜头语言问题），要么是取景框上画通用辅助线（不懂你的意图）。
  3. AI 视频的镜头是随机抽的。跳轴、构图漂移、节奏单调——创作者用提示词控制不住，也不懂该用什么词。

03 · 用户旅程：按下按钮后的 8 秒

1
打开，对准场景手机/电脑相机对着要拍的对象，画面实时显示在取景框
2
按一个按钮唯一的启动动作，不需要设置参数、不需要选模式
3
说出你的要求语音或文字："想要电影感的人物特写，背景虚化，情绪安静一点"
4
本地瞬间框出主体0.2 秒内用端侧小模型画出主体框，用户立刻看到 AI 在工作
5
每 2–3 秒采一帧上云云端大模型理解画面 + 意图，2–5 秒返回判断
6
叠加显示 Top-3 建议取景框上直接标注："① 后退两步，主体占比 18%→35% ② 换 3.2x ③ 机位降到腰部"，每条带一句为什么
7
用户调整，建议刷新画面变化后自动重新判断，形成"调整—反馈"闭环
8
满意后按录制可导出"调整前 vs 调整后"对比，用于分享或交付

延迟说明：2–5 秒对拍摄指导完全够用——摄影师本来就要调整姿势和走位。不要为了亚秒级延迟牺牲可行性。

04 · 六个功能模块

模块做什么输入输出负责人
A 意图解析把用户自然语言拆成镜头类型 + 目标权重"电影感人物特写，背景虚化"intent=人像特写, weights={主体:.4,背景:.3,光:.2}你（Bridge）
B 画面特征从当前帧提取可计算的视觉量视频帧主体框、占比、边缘密度、光线方向队友 A + 你
C 建议生成目标函数算差距，映射成动作，排序A + B 的结果 + 规则库Top-3 动作 + 理由你（Bridge）
D 实时交互视频流、采样调度、按钮、建议叠加相机画面 + 用户点击带标注的取景画面队友 A
E 规则与话术什么情况给什么建议、怎么说人话拉片标注案例rules.json + 话术表队友 B
F 素材整理与剪辑按意图和质量筛选可用片段，输出粗剪时间线素材清单 + 拍摄时的意图记录整理分类 + EDL 时间线你 + 队友 A

新增：拍摄素材的自动剪辑与整理

拍完不是结束。系统把这次拍摄产生的素材自动分类、挑出能用的片段、排出一条粗剪时间线，直接导进剪映或 FFmpeg。

这是闭环的关键：拍摄指导阶段已经记录了"每个镜头想要什么效果"和"用户是否按建议调整过"——这些数据成了剪辑阶段判断素材好坏的依据。别家工具只看画面质量，我们还知道你当时想拍什么。

自动整理（拍后立即）

按场景 / 镜头类型聚类；剔除重复与废片；给每条素材打上意图标签和质量分；标注"按建议调整过"的片段。

自动粗剪（一键执行）

选每段的最佳入出点（避开抖动和闭眼）；按叙事顺序排列；控制总时长；给出转场建议；输出 EDL 时间线 JSON。

详细规则、字段与分工见交付包中的 edit_logic.md、edit_rules.json 和 edit_engine.py。我们不碰最终成片——那是剪辑师的事，我们只让"从素材到能看的粗剪"这一步不再从零开始。

目标函数（你的核心资产）

评分 S = w1·主体占比分 + w2·背景干扰分 + w3·光线角度分 + w4·视线空间分

约束：焦段范围 / 机位高度 / 物理遮挡
求解：网格搜索 → 遗传算法或粒子群
输出：与当前画面的差距 → 映射为可执行动作

关键：权重 w 由"用户意图 × 镜头类型"决定，
      规则库（队友 B 产出）提供每一种意图的初始权重。

05 · 技术架构与工程取舍

端侧（本地）

MediaPipe 做主体检测与姿态估计；视频流采集；2–3 秒采样调度；建议文字与辅助线叠加。

延迟：毫秒级

云侧（API）

多模态大模型理解"用户要求 vs 当前画面"的差距；Python 求解器生成建议。

延迟：2–5 秒

数据层

rules.json 规则库；shots.csv 标注表；phrases.json 动作话术表。

形式：纯文件，先不上数据库

三个让"实时"可做的取舍

  1. 不逐帧，采样帧。每 2–3 秒送一帧，成本和延迟都压得住，体验上足够。
  2. 不输出坐标，输出动作。"后退两步"比"机位移动到 (x=2.3, y=1.6)"有用一百倍。
  3. 端云分工。能本地算的（主体框、辅助线）绝不上云；云端只做语义判断。

技术栈建议：原型阶段用网页前端（ getUserMedia + Canvas 叠加）+ Python FastAPI 后端。三个人都是新手也不要紧——这套栈资料最多、调试最直观。

06 · 详细分工

默认按"会写代码 = 队友 A，更懂拍摄 = 队友 B"分配。若两人都是编程背景，队友 B 承担拉片标注与用户调研；若两人都不懂拍摄，三人一起拉片，标注任务拆成三份。

你

算法内核

定位：产品的大脑。把队友 B 的规则变成可计算的决策，交给队友 A 去展示。

职责范围

  • 意图分类体系设计
  • 目标函数定义与调权
  • "差距 → 动作"映射逻辑
  • 建议排序与理由生成
  • 建议引擎 API 封装

三周任务

  • W1：定 5 类镜头意图 + 权重向量表；写一页纸数学定义
  • W1：列出需要的画面特征字段，交给队友 A
  • W2：实现 suggest_engine.py，输入特征 JSON 输出 Top-3 动作
  • W2：接入多模态 API 做意图解析和理由生成
  • W3：与 A 联调，用 20 张测试图校验一致率
交付物：
① intent_weights.json
② suggest_engine.py
③ 一页纸数学定义（Markdown/PDF）
④ 建议引擎 API
验收标准：给定 20 张测试图，输出建议与"懂摄影的人"的判断一致率 ≥ 70%；单次响应 < 5 秒。
队友 A

实时工程

定位：产品的身体。让用户真的能按一个按钮跑起来。

职责范围

  • 相机视频流采集
  • 2–3 秒采样调度器
  • 按钮与交互界面
  • 建议叠加层（文字 + 辅助线）
  • 端侧主体框（MediaPipe）

三周任务

  • W1：搭网页骨架，跑通 getUserMedia 出画面
  • W1：用假数据先把"按钮 → 出建议 → 叠加显示"流程跑通
  • W2：接入端侧主体框与采样调度
  • W2：对接你的建议引擎 API
  • W3：优化卡顿，打包成可演示版本，录演示视频
交付物：
① 可运行的原型网页
② 视频流与采样模块
③ 叠加层组件
④ 3 分钟演示录屏
验收标准：按按钮后 5 秒内出现第一条建议；连续运行 10 分钟不崩溃；界面上只有"一个按钮 + 输入要求 + 建议区"。
队友 B

领域规则

定位：产品的经验。决定建议到底专不专业、说不说人话。

职责范围

  • 拉片与机位标注
  • 规则库构建与维护
  • 动作话术库（怎么说人话）
  • 校验建议是否专业
  • 找用户试用、收集反馈

三周任务

  • W1：拉 30 个镜头，建 90 条标注表（字段见接口约定）
  • W1：收集 50 条动作话术（后退两步 / 换 3.2x / 主体放左三分之一等）
  • W2：从标注表提炼 rules.json，覆盖 80% 常见场景
  • W2：对你的 20 条输出做"专不专业"评分
  • W3：找 5 个真实用户试用，记录反馈
交付物：
① shots.csv（90 条标注）
② phrases.json（50 条话术）
③ rules.json（规则库）
④ 用户试用反馈记录
验收标准：规则库覆盖 ≥ 80% 常见场景；话术表里的每条建议普通人听完就能执行，不需要二次解释。

三人怎么串起来

依赖链：队友 B（内容）→ 你（大脑）→ 队友 A（身体）。但 A 第一周可以用假数据先搭架子，不必等任何人。每周固定一次 30 分钟碰头，只做三件事：看上周产出、确认接口有没有变、定下周优先级。

07 · 接口约定（三人协作的生命线）

接口一：队友 B → 你，规则库

{
  "scene_type": "portrait_closeup",
  "intent": "cinematic",
  "target_subject_ratio": [0.3, 0.6],
  "preferred_light": "side",
  "bg_complexity_max": 0.35,
  "actions": [
    {
      "condition": "subject_ratio < 0.3",
      "action": "后退两步",
      "reason": "主体占比偏低，退后能带出更多环境"
    }
  ]
}

接口二：队友 A → 你，请求

{
  "intent": "电影感人物特写，背景虚化",
  "frame_features": {
    "subject_ratio": 0.18,
    "edge_density": 0.42,
    "light_direction": "front",
    "subject_position": [0.5, 0.48]
  }
}

接口三：你 → 队友 A，响应

{
  "suggestions": [
    {
      "rank": 1,
      "action": "后退两步",
      "delta": "主体占比 +17%",
      "reason": "当前 18%，目标 30–60%，退后能带出环境层次"
    },
    {
      "rank": 2,
      "action": "换成 3.2x 焦段",
      "delta": "背景虚化增强",
      "reason": "长焦压缩背景，符合你要的虚化感"
    }
  ]
}

字段一旦定下，第一周内任何人要改都在群里说一声，不要私自改。接口文件放在同一个仓库/共享文档里，标明版本号。

08 · 三周排期

第 1 周
并行打底。你：意图分类表 + 一页纸数学定义 + 特征字段清单。队友 A：网页骨架 + 假数据跑通全流程。队友 B：90 条标注表 + 50 条话术。
周末产出：三份独立文件，互相交换看一遍。
第 2 周
集成。你：建议引擎实现 + API 封装。队友 A：接 API + 端侧主体框。队友 B：规则库 JSON + 校验你的 20 条输出。
周末产出：第一次跑通"按按钮 → 出建议"完整链路。
第 3 周
验证与交付。你：联调与一致率测试。队友 A：优化卡顿、录演示视频、打包。队友 B：找 5 个用户试用、收反馈。
周末产出：可演示原型 + 3 分钟录屏 + 大创申报素材。

每周固定动作：周一晚 30 分钟碰头定优先级；周日晚各自把产出放进共享目录；碰头只看产出，不开务虚会。

09 · 风险与兜底

风险 1：队友都没有影视背景。
兜底：三人一起拉片，30 个镜头拆成每人 10 个。你只标"数学上可计算的量"，另外两人标"为什么这么拍"。规则库由三人共同投票确定。
风险 2：2–5 秒延迟还是嫌慢。
兜底：把"连续建议"降级成"点一下给一次建议"（点击触发）。功能上仍然满足"按一个按钮给建议"，只是不持续刷新。这是完全可接受的第一版。
风险 3：API 成本失控。
兜底：采样帧间隔从 2 秒拉到 4 秒；画面特征尽量本地算；云端只传压缩后的关键帧和意图文本。原型阶段用免费额度足够。
风险 4：建议不准，用户不买账。
兜底：不追求"一次给对"，改成"给 3 个候选 + 让用户选哪个有用"。用户的选择反过来变成规则库的训练数据——这本身就是产品壁垒。
风险 5：跟 Doka 之类的产品撞车。
兜底：我们不做通用构图线，只做意图驱动——"你想拍成什么样"决定建议。这是手机厂商不会做、第三方 App 没做的口子。验证时重点问用户："跟 Doka 比，哪个建议更符合你想要的感觉？"

10 · Demo 验收标准

三周后，如果下面七条都能做到，就算原型成功，可以直接拿去申报大创或找用户验证。

  1. 打开原型，画面里只有一个按钮、一个输入框、一个建议区。
  2. 按按钮、输入"电影感人物特写，背景虚化"，5 秒内出第一条建议。
  3. 建议是可执行动作 + 理由，不是分数、不是坐标、不是构图线。
  4. 用户按建议调整后，画面肉眼可见地更接近要求；导出"调整前 vs 调整后"对比图。
  5. 找 5 个人试用，至少 3 个人说"这个建议我平时想不到，但确实有用"。
  6. 拍摄结束后导入 5 条素材，系统能自动挑出可用片段并输出一条粗剪时间线。
  7. "按建议调整过"的片段在剪辑结果中被优先保留，且用户能看到保留理由。
